FBI Warns of Kali365 Threat Targeting Microsoft 365 Users

May 28, 2026 12-Minute Read

The FBI’s latest warning sidesteps the usual phishing narrative. In May 2026, the agency flagged Kali365, an emerging phishing-as-a-service platform first seen in April 2026, distributed via Telegram, that enables attackers to obtain Microsoft 365 access tokens and bypass multi-factor authentication without intercepting the user’s credentials. The distinction matters because this attack doesn’t rely on stealing your password. Instead, it manipulates how Microsoft’s own OAuth system hands over account access—and does so in a way that MFA can’t reliably stop.

For anyone using Outlook, Teams, OneDrive, or any Microsoft 365 service, understanding this threat is no longer optional. The attack is live, spreading rapidly, and it exposes a gap between what users believe their security controls protect against and what actually happens when attackers focus on legitimate authentication pathways.

Why This Bypasses Multi-Factor Authentication

The core confusion around this attack stems from a misunderstanding of how MFA works. Most people assume that multi-factor authentication secures an account by requiring a second form of proof—a code from your authenticator app, a text message, a security key. But MFA protects the credentials themselves, not the broader authentication ecosystem.

The method abuses Microsoft’s OAuth 2.0 device authorization grant flow by presenting users with device codes that, when entered, inadvertently grant attackers control of enterprise accounts. Here’s the critical distinction: the victim enters their username, password, and MFA response on a legitimate Microsoft login page. To Microsoft’s systems, this looks correct. The MFA challenge succeeds. The user authenticated properly.

What the victim doesn’t realize is that they’re approving access for the attacker’s device, not their own.

The victim interacts with legitimate Microsoft domains; credentials and MFA are entered on authentic pages; traditional phishing indicators may not trigger. The attacker initiates the device code flow from their own infrastructure, displays the device code to the victim through a fake document or lure, and the victim—believing they’re authorizing a legitimate system request—enters that code on microsoft.com/devicelogin. The authentication succeeds, and the attacker receives valid OAuth tokens.

This is why access tokens are valid for 60 days and refresh tokens are valid for a year. The attacker doesn’t need repeated access. One successful phishing interaction grants them persistence for months.

The Kali365 Platform: Democratizing Microsoft Account Takeover

What distinguishes Kali365 from earlier device code phishing attempts is its scale and accessibility. The Kali365 software program provides its users with a subscription plan starting from $250 per month, with AI-powered phishing emails, automated templates to conduct campaigns, and dashboards to track victims in real time.

This is significant because it lowers the barrier to entry for attackers with minimal technical skill. Earlier phishing campaigns required custom infrastructure, custom landing pages, and knowledge of Microsoft’s OAuth flow. Kali365 abstracts all of that. An attacker can subscribe to the platform, select a template (or generate a phishing email using AI), and launch a campaign within hours.

The platform operates on Telegram, where it’s advertised and sold like any other underground service. This distribution method is deliberate—Telegram chats offer privacy, access control, and rapid iteration. Customers can track real-time victim progress through Kali365’s dashboard, see which targets have clicked, monitor token acquisition, and then use the stolen tokens immediately.

The victims aren’t evenly distributed. Construction, non-profits, real estate, manufacturing, financial services, healthcare, legal, and government are some of the prominent sectors targeted. Industries with high employee turnover, distributed workforces, and legacy security practices are particularly vulnerable. A construction company’s project manager is more likely to click a link about a shared blueprint. A healthcare worker may see a message framed as a patient data verification request. Nonprofits often have smaller IT budgets and less sophisticated monitoring.

How The Attack Actually Unfolds

The attack follows a predictable but deceptive sequence. An email arrives claiming to come from a document-sharing service, cloud provider, or internal system—DocuSign, Slack, SharePoint, or OneDrive. The message says something like “Review the attached document” or “Verify your account access” or “Confirm your identity for security purposes.”

The victim clicks the link and lands on a convincing fake page that displays a device code—a short alphanumeric string. The page instructs them to copy the code and paste it into Microsoft’s device login portal to complete verification. This framing—“enter this code to authorize”—mimics legitimate Microsoft workflows, making it plausible to anyone who has used device-based authentication before.

The victim visits microsoft.com/devicelogin (the real Microsoft domain), enters the code, and is prompted to sign in. They enter their username, password, and any MFA challenges. From their perspective, everything is normal. They see a legitimate Microsoft domain, and their MFA works as expected.

But behind the scenes, the Kali365 backend dynamically generates a real Microsoft OAuth device code and displays it to the victim through the lure landing page. After the victim completes authentication at Microsoft’s real portal, the resulting OAuth access and refresh tokens route back to the Kali365 backend.

The attacker now has access. They can read all emails in the victim’s Outlook inbox, download files from OneDrive, access Teams messages and conversations, and impersonate the victim to colleagues. For privileged accounts—IT administrators, finance officers, executives—the scope of damage expands significantly. From the victim’s view, everything appears legitimate because they are interacting with Microsoft’s actual infrastructure throughout the entire process.

Why Detection Is Harder Than Previous Phishing

Traditional security approaches focus on blocking malicious infrastructure. Email gateways look for suspicious domains. Browsers warn about phishing sites. URL filters block known malicious links. But every element of the authentication interaction occurs on legitimate Microsoft infrastructure. There’s no malicious domain for filters to catch. The victim never visits the attacker’s infrastructure during the critical authentication moment.

Because activity happens on legitimate domains and encrypted channels, detection using traditional indicators becomes harder. The attacker’s infrastructure is used only to display the initial lure and to receive the tokens after authentication. The dangerous part—where the victim actually authenticates and reveals MFA codes—happens on Microsoft’s own encrypted, legitimate systems.

This creates a detection gap that many organizations haven’t closed. Standard email security tools can flag some of the Kali365 lures if they have good phishing templates. But once a victim lands on a fake document or form, traditional indicators vanish.

Who Is Actually at Risk

Everyone using Microsoft 365 is technically at risk. But practical risk varies by role and organization. Individual users with personal Microsoft accounts are targets if they have valuable email contacts or connected services. Enterprise users are higher-value targets because they likely have access to corporate resources, customer data, or internal communications.

The highest-risk individuals are those who:

  • Receive frequent requests to verify identity, approve documents, or confirm access (finance, HR, legal, customer-facing roles)
  • Have administrative accounts or high permissions within their organization
  • Work in organizations that share a lot of documents via cloud services
  • Are known to use Microsoft 365 across multiple devices (the device authorization framing resonates more)

Sectors with high targeting include financial services (where BEC and wire fraud follow account compromise), healthcare (patient data), legal (confidential client information), and government (classified materials). But construction, non-profits, real estate, manufacturing, and legal services are some of the prominent sectors targeted, suggesting attackers cast a wide net wherever valuable data or financial assets exist.

Practical Steps to Protect Your Account

The FBI’s recommendations focus on two areas: preventing the attack and detecting it if it happens.

Restrict device code flows. Organizations can limit or disable the ability for applications to request device codes. Restricting device code flow to limit or block device authentication codes can help prevent or limit this style of attack. This is a setting in Azure Active Directory under Conditional Access policies. If your organization doesn’t legitimately use device code flows (which many don’t), disabling it eliminates the attack vector entirely.

For individual users, this option isn’t directly available through Outlook or Teams settings. But you can talk to your IT department about implementing this policy organization-wide.

Don’t enter codes from unsolicited requests. Users should be trained that any unsolicited code presented as an “OTP,” “access token,” or “security code” to enter at microsoft.com/devicelogin should be treated as a potential attack and reported without entering the code. This is the user-facing equivalent of the technical fix. If you receive a message asking you to enter a code at microsoft.com/devicelogin (or any Microsoft authentication endpoint), and you didn’t initiate the request yourself, don’t do it. Call your IT department to verify the request is legitimate.

Review sign-in activity. Legitimate access tokens mean attackers can log into your account without your password. But the authentication will show up in your sign-in logs. In Microsoft 365, you can check recent sign-in activity from Settings > Security > Your sign-in activity. Look for logins from unfamiliar locations or at unusual times. Kali365 tokens are often used from attacker-controlled infrastructure, which may show up as logins from data center IP ranges or countries you don’t recognize.

Revoke refresh tokens if compromised. If you suspect a device code phishing attack, revoke all refresh tokens for affected users. This invalidates all outstanding tokens and forces re-authentication. In Azure AD, this is done through the Azure portal under Users, selecting the affected user, and clicking “Sign out sessions.” This doesn’t change the password (you may want to do that separately), but it terminates all active token-based sessions.

Enable conditional access policies. Advanced organizations can configure conditional access to require additional verification for logins from unusual locations or devices. This doesn’t prevent the device code attack itself, but it can catch attackers when they try to use stolen tokens from unexpected environments.

What to Do If You’ve Clicked a Device Code Link

If you’ve recently clicked a suspicious link that asked you to enter a code at microsoft.com/devicelogin, treat it as a potential compromise. Here’s the sequence:

  1. Change your Microsoft account password immediately.
  2. Check your sign-in activity for any logins you don’t recognize. Pay special attention to the last 7 days.
  3. If you see suspicious logins, revoke all refresh tokens through Azure AD.
  4. Enable multi-factor authentication if you don’t already have it (this won’t retroactively protect against token theft, but it prevents future password-based compromise).
  5. If you work for an organization, report the incident to your IT department or security team immediately. They need to know so they can monitor for lateral movement or additional compromise.
  6. If you use the same password on other services, change those passwords too.
  7. Monitor your email for unauthorized forwarding rules. Device code attacks often precede business email compromise, where attackers set up forwarding rules to silently copy all incoming messages.

For organizations, this means checking affected user accounts for suspicious forwarding rules, checking for changes to permissions or group memberships, and reviewing activity in shared resources (OneDrive, SharePoint, Teams) for unusual file access or downloads.

The Broader Context: Why Device Code Phishing Is Rising

Device code flows exist for a legitimate reason. Smart TVs, printers, and other devices with limited input methods need a way to authenticate with cloud services. Instead of typing a password on a TV remote, the device displays a code, the user visits microsoft.com/devicelogin on their phone or computer, enters the code, and the device gains access.

This is a reasonable design. The problem is that the same flow can be misused. An attacker can initiate the flow, trick a victim into thinking it’s legitimate, and steal the tokens. Microsoft’s infrastructure works correctly—it authenticated a real user, issued real tokens. The victim’s password was never stolen. MFA worked as designed. But the intent was compromised.

This pattern repeats across OAuth and other modern authentication systems. The attacks that worked in 2000—stealing passwords through phishing—are increasingly difficult against users with MFA. So attackers shifted to abusing the legitimate authentication systems themselves. Device code phishing is one example. OAuth app consent phishing (where users grant applications broad permissions) is another. These attacks exploit the assumption that if you’re on a legitimate platform entering your credentials, the purpose must be legitimate too.

The rise of PhaaS platforms like Kali365 indicates that these attacks have matured past the point of requiring sophisticated attackers. The barrier to entry is now subscription fee and basic campaign management skills. This is why the FBI issued a public warning—the threat moved from targeted to widespread.

What Microsoft Is Doing

Microsoft has acknowledged the threat and released some guidance, but the fixes are incomplete. Organizations can use Conditional Access policies to add friction, but this requires administrative access and policy configuration skills that many smaller organizations lack. Microsoft also updated some of its phishing education content to mention device codes, but this depends on user awareness.

The fundamental challenge is that Microsoft’s OAuth device flow is working as designed. The vulnerability isn’t a bug—it’s a design assumption that trusted platforms won’t trick users into authorizing access. Closing it entirely would break legitimate use cases. Restricting it too much frustrates legitimate device authentication.

For now, the responsibility sits with organizations to implement Conditional Access policies and with users to avoid entering codes from unsolicited requests. This is an imperfect solution, which is why the FBI felt compelled to issue a public warning.

The Takeaway

The Kali365 threat highlights a shift in how account compromise happens. Passwords are increasingly defended. MFA is increasingly deployed. But the authentication systems protecting them can still be manipulated through phishing. The attack surface has expanded from credentials to legitimate authentication flows.

The good news is that the threat is preventable. Restricting device code flows, training users not to enter unsolicited codes, and monitoring sign-in activity all provide layers of defense. The bad news is that none of these are defaults. They require intentional configuration by administrators or behavioral changes by users.

If you use Outlook, Teams, or OneDrive—and especially if you work for a larger organization—check with your IT department about device code flow restrictions. If you’re an individual user, be skeptical of any message that asks you to enter a code at a Microsoft login page. And if you’ve clicked one of these links recently, change your password and review your account activity. The attack is sophisticated in its construction but straightforward to detect once you know what to look for.
