Cut Claude Code Token Usage Without Killing Productivity

May 7, 2026 9-Minute Read

Most Claude Code bills don’t balloon from a single large request. They compound quietly—session after session—from decisions that seem harmless at the time: leaving a chat thread open all day, loading a sprawling CLAUDE.md, asking Claude to “look into the codebase” without pointing it anywhere specific. By the time you check your usage, you’re staring at a number that’s hard to explain.

Token costs in Claude Code scale with context size, not message count. That’s the key distinction most developers miss early on. Every message Claude receives includes the full conversation history, your CLAUDE.md, active MCP tool definitions, and anything else sitting in the context window—processed from scratch, every single time. A 6-person team documented this firsthand: month-one Claude Code spend hit $2,400. After tightening context habits, prompt caching, and model routing, month three came in at $680—a 72% reduction with no change in output quality.

The techniques below reflect what actually works, grounded in both Anthropic’s official cost documentation and real-world developer experience.

Your CLAUDE.md Is a Token Tax on Every Request

Here’s one that bites developers more than almost anything else: CLAUDE.md loads at the start of every session, before Claude reads a single line of your code or task description. A 5,000-token CLAUDE.md is a 5,000-token surcharge on every turn, every session, indefinitely.

The fix isn’t to gut the file—it’s to be selective about what belongs there. CLAUDE.md should contain project conventions, key architectural decisions, and things Claude genuinely cannot infer. It should not be a general coding style guide, an aspirational team philosophy, or a copy-paste of your README.

Anthropic’s own documentation recommends keeping CLAUDE.md under 200 lines. Anything beyond that is likely better suited for a skill—an on-demand knowledge block that Claude only loads when it specifically needs it. A “codebase-overview” skill, for instance, can describe your project’s directory structure and naming conventions without injecting those tokens into every unrelated session.

The structural difference: CLAUDE.md is always present. Skills load only when invoked. That distinction matters enormously at scale.

Sessions Are Context Accumulators—Treat Them That Way

A long chat thread isn’t just inconvenient to scroll through. Every follow-up message—”fix that edge case,” “now handle the error state,” “also update the test”—forces Claude to reprocess the entire conversation from the top. The cost of that reprocessing grows quadratically with thread length.

Three habits that keep sessions from silently inflating costs:

  • Clear between unrelated tasks. Use /clear when you shift to a different piece of work. Stale context from a previous task adds zero value but costs real tokens. Before clearing, /rename the session so you can /resume it later if needed.
  • Use /compact before sessions run long. This summarizes the conversation history into a compressed form. You can even tell Claude what to prioritize: /compact Focus on code changes and test output keeps the parts that matter.
  • One task per chat. Splitting sessions by task isn’t just organizational—it’s the simplest context-control strategy available. A fresh session for each discrete piece of work avoids the accumulation problem entirely.

The /usage command shows you where you stand mid-session, which is worth checking before a particularly long task. Alternatively, configure your status line to display context window usage continuously—so you’re not surprised at the end.

Match the Model to the Work, Not to Your Comfort Level

Claude Opus is genuinely better at complex multi-step reasoning and architectural decisions. It’s also significantly more expensive. Using Opus for a string formatting task or a one-file bug fix is the equivalent of hiring an expert consultant to alphabetize your bookshelf.

Sonnet handles the overwhelming majority of coding tasks well—refactoring, test generation, documentation, standard debugging. Reserve Opus for tasks where deep reasoning actually changes the outcome: evaluating a major architectural trade-off, designing a complex system, or reasoning through an unfamiliar codebase at a high level.

For subagent tasks, Haiku is often sufficient. A common model routing pattern that teams have used effectively: Haiku for classification and simple generation, Sonnet for most production work, Opus only when reasoning depth genuinely matters. Teams using a 70/20/10 Haiku/Sonnet/Opus split have cut API costs by more than half compared to running everything through Sonnet.

You can switch models mid-session with /model, or set a per-session default in /config. For subagents, you can specify model: haiku directly in your subagent configuration.

Extended Thinking Has a Price—Calibrate It

Extended thinking is on by default in Claude Code, and for good reason: it meaningfully improves performance on complex planning and reasoning tasks. But thinking tokens are billed at output token rates, and the default budget can run into the tens of thousands of tokens per request.

For simpler tasks—a quick edit, a unit test, a focused refactor—that extended thinking budget is largely wasted. The model doesn’t need to reason deeply about adding a null check.

You have a few levers here:

  • Lower the effort level with /effort for sessions where deep reasoning isn’t needed
  • Set MAX_THINKING_TOKENS=8000 to cap the thinking budget
  • Disable extended thinking entirely in /config for straightforward work

The practical approach: leave extended thinking on for complex or ambiguous tasks. Dial it back or disable it for sessions with well-defined, bounded scope. The difference per session is small. Across hundreds of sessions, it’s meaningful.

MCP Servers Add Context You May Not Need

Each configured MCP server contributes tool definitions to Claude’s context. Claude Code now defers full tool definitions by default—only tool names enter context until Claude actually invokes a specific tool—but the overhead still exists, and it compounds across many configured servers.

Two practical moves:

Disable servers you’re not actively using. Run /mcp to see what’s configured. If you have a GitHub MCP server loaded for a session where you’re doing local work, it’s context you’re paying for without benefit.

Prefer CLI tools for tasks where they exist. Tools like gh, aws, gcloud, and sentry-cli are more context-efficient than their MCP equivalents because they don’t inject per-tool listings into context at all. Claude can execute CLI commands directly, which is often faster and cheaper for straightforward operations.

Preprocessing Hooks: Handle Verbosity Before It Reaches Claude

This one is less obvious but genuinely high-leverage. Claude Code supports custom hooks that run before Claude processes tool output. That means you can filter, truncate, or transform data before it enters the context window—rather than asking Claude to read a 10,000-line log file to find three error lines.

A PreToolUse hook on Bash commands, for example, can detect when you’re running a test suite and automatically filter the output to show only failures and their stack traces. What might otherwise consume tens of thousands of tokens becomes a few hundred.

The pattern generalizes to anything verbose: log files, API responses, documentation lookups. If you can describe the filtering logic in a script, you can keep that data out of Claude’s context entirely and pass only what it needs.

Similarly, code intelligence plugins for typed languages replace broad file-search patterns with precise symbol navigation. Instead of Claude running grep across multiple files to find a function definition, a language server call resolves it directly. Fewer file reads, smaller context, same result.

Subagents for Isolated, Context-Heavy Work

Some tasks are inherently verbose—running a full test suite, fetching and processing documentation, analyzing large log outputs. When these happen in your main session, their output accumulates in your shared context and inflates the cost of every subsequent message.

The cleaner pattern: delegate them to subagents. A subagent has its own context window. The verbose output stays there, and only a summary comes back to your main conversation. This keeps your main session context tight and focused.

For agent teams—multiple Claude Code instances running in parallel—token usage scales roughly with team size, since each instance carries its own context window. Anthropic documents that agent teams use approximately 7x more tokens than standard sessions in plan mode. The guidance: keep teammate tasks small and self-contained, use Sonnet for coordination tasks rather than Opus, and clean up teams promptly when work is done.

Prompt Specificity Is Not Just a Quality Issue

Vague requests generate exploration. “Improve this codebase” triggers broad file scanning—Claude reading across directories trying to understand scope. “Add input validation to the login function in auth.ts“ gives Claude exactly what it needs. No exploration required.

The token cost difference between these two prompts isn’t in the prompt itself. It’s in the downstream context Claude accumulates while figuring out what to do. Specific prompts reduce that exploration cost significantly.

The same principle applies to course-correction. If Claude starts moving in the wrong direction, stopping early is cheaper than letting it continue. Press Escape to interrupt, use /rewind to restore the conversation to a previous checkpoint, and reframe the prompt. Rework after a long incorrect session is one of the more expensive ways to use Claude Code.

Baseline First, Then Optimize

The mistake many developers make is applying token-saving techniques without measuring their actual impact. Generic percentage claims—40% savings, 70% reduction—are directional signals, not promises. Your specific workflow, codebase size, and usage patterns determine what the numbers actually look like.

Run /usage at the start and end of a representative session to get your baseline. Apply one or two changes. Run the same session again. The comparison tells you what’s working for your specific setup.

The official Claude Console gives authoritative billing data; the local /usage estimate is close but may diverge from actual charges. For teams, the Console’s usage reporting shows cost and token consumption by workspace, which is where allocation decisions become visible.

Reducing Claude Code token usage isn’t about using the tool less—it’s about using it without the waste that naturally accumulates when you’re not paying attention to context. The developers who manage costs well aren’t running fewer sessions. They’re running cleaner ones.
